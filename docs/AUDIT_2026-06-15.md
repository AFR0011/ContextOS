# ContextOS Full App Audit - 2026-06-15

## Verdict

ContextOS v0.2.2 is functionally healthy in the local production build, but it is **not ready for an internet-facing deployment**.

The release blocker is server-side sync ownership enforcement. The sync path checks records with `id + userId`, then performs updates using a globally unique `id` only. With public registration enabled, a client that knows another account's record ID could overwrite that record through sync.

A private local trial remains reasonable. A hosted preview should wait until the P0 deployment gates below are complete.

Update 2026-06-16: v0.2.3 completed the first deployment gate by fixing user-owned sync writes, user-scoped mutation IDs, bounded sync payloads, closed production registration, task/note search destinations, task-title wrapping, and completion-order stability. v0.2.5 completed baseline security headers, explicit metadata base handling, and corrected service-worker cache/routes. Public production remains blocked by auth abuse controls, CI/preview gates, installed-PWA upgrade smoke, monitoring, backup/restore, and rollback evidence.

## Scope And Evidence

- Reviewed product, design, state, run, QA, risk, migration, and deployment documentation.
- Reviewed auth, session, sync, IndexedDB/outbox, API validation, navigation, search, editor, service worker, and deployment configuration.
- Ran Prisma validation and migration-status checks against local PostgreSQL.
- Ran TypeScript, production build, npm dependency audit, and the full Playwright suite.
- Walked Dashboard, Search, Projects, Dates, and responsive behavior in the in-app browser at desktop and mobile sizes.
- Checked production response headers and browser console output.

## Findings

### P0 - Deployment Blockers

1. **Sync updates are not safely user-scoped.**
   `src/lib/sync-server.ts` reads with `{ id, userId }` but upserts with `{ id }` for domains, projects, tasks, captures, notes, dates, reviews, scratchpads, and preferences. The mutation ledger is also looked up by global `mutationId` rather than user plus mutation ID.

2. **Public registration conflicts with the single-user MVP deployment model.**
   `/register` is available to anyone, new accounts receive demo workspace data, and there is no deployment flag or invitation boundary. This turns the sync ownership defect into a practical multi-user exposure.

### P1 - High Priority Before Production

3. **Auth endpoints have no abuse controls.**
   Login and registration have no rate limiting, lockout, CAPTCHA, or provider-level protection. Password reset and verification remain intentionally deferred, so deployment should default to closed registration.

4. **Sync payloads are effectively unbounded.**
   `/api/sync` accepts an unlimited mutation array with arbitrary record payloads. Add request-size, array-length, string-length, and entity-specific validation.

5. **Production security headers are absent.**
   Responses expose `X-Powered-By` and do not set an application CSP, frame protection, referrer policy, permissions policy, or content-type sniffing protection.
   Status update 2026-06-16: fixed in v0.2.5 and covered by targeted Playwright assertions.

6. **No automated deployment gate exists.**
   The repository has no CI workflow. Migrations, typecheck, build, and tests rely on manual execution.

7. **Operational recovery is incomplete.**
   The deployment guide has no verified backup/restore drill, health endpoint, monitoring/error reporting, or documented database-aware rollback procedure.

8. **Seven dependency advisories remain.**
   `npm audit` reports five moderate and two high advisories, including the `tsx`/`esbuild` path. Forced audit fixes propose unsuitable changes; use controlled upgrades and rerun the full ladder.

### P1 - Product And Navigation Bugs

9. **Task search can navigate to a page that does not contain the result.**
   All task results route to `/today`. The live audit opened `Rerun RF baseline with corrected threshold logic`, then confirmed the task was absent from Today. Route to a stable task context or project and focus/highlight the record.

10. **Standalone note search results are fake buttons.**
    The `Piano Schedule` result renders as a button but has no action because it is not project-linked. Route standalone notes to Resources or render a non-interactive result.

11. **Reset Demo Data is a visible, immediate destructive action.**
    Settings exposes it to all users without confirmation. In production the endpoint is normally disabled, leaving a confusing action that fails after the click.

12. **The service worker still advertises the legacy route.**
    `public/sw.js` uses cache `contextos-shell-v1` and pre-caches `/deadlines` instead of `/dates`. Bump the cache version, update routes, and verify upgrade behavior from an installed older PWA.
    Status update 2026-06-16: cache/routes fixed in v0.2.5; installed older-worker upgrade smoke remains pending.

13. **Build metadata is incomplete.**
    The production build warns that `metadataBase` is missing, so URL-based metadata can resolve against localhost.
    Status update 2026-06-16: fixed in v0.2.5; build passed without the previous warning.

### P2 - UI/UX And Accessibility Friction

14. **Dashboard hierarchy remains too card-heavy.**
    Quick Capture is correctly first, but Notepad, Dates, Daily Timeline, Tasks, and Projects retain similar visual weight. The proposed pressure strip and lighter section treatment are sensible next refinements.

15. **Project recovery fields are buried.**
    The current order matches v0.2.2, but Next Action and Latest Status sit inside Recovery Canvas below Active Tasks and Dates. For recovery speed, promote them near the header before the longer record lists.

16. **Mobile editor actions are too small and partially clipped.**
    Focused block controls measure 20 by 20 pixels at 390px width; the add control begins at x=-2. Several other mobile controls are 16-36px, below a comfortable touch target.

17. **Accessible names and menu semantics are incomplete.**
    The visible mobile menu and subcontext-add buttons lack accessible names. Slash command and block action menus do not expose complete menu/listbox semantics, selection state, or robust focus return.

18. **Destructive behavior is inconsistent.**
    Task/project deletion and reset actions do not share a clear confirmation, undo, or danger-zone pattern.

19. **Large components increase regression risk.**
    `Views.tsx`, `Dashboard2.tsx`, `BlockMarkdownEditor.tsx`, and `client-store.tsx` hold multiple concerns. Split by screen or behavior only as each audited fix is implemented.

20. **Dates need stronger scanning hierarchy.**
    Dates are correctly separate from task due dates, but the screen has no overdue/today/tomorrow/this-week/later grouping.

## What Is Working

- Prisma schema validation and migration status pass.
- TypeScript and the production build pass.
- All 29 existing Playwright tests pass sequentially.
- Desktop and mobile walkthroughs show no horizontal overflow or browser console warnings/errors.
- Quick Capture is above Dashboard content.
- Daily Timeline, all Tasks, Dates separation, project section ordering, and mobile bottom navigation are present.
- Session cookies are HTTP-only, secure in production, same-site lax, and backed by hashed random tokens.
- Markdown rendering does not inject raw HTML.
- Demo reset is server-disabled in production unless explicitly enabled.

## Proposed Next Batch - v0.2.3 Deployment Hardening

1. Make every sync mutation and mutation-ledger lookup user-scoped; validate related project/domain IDs; add two-user isolation tests.
2. Add a closed-registration production mode and remove demo credentials/reset affordances from normal production UI.
3. Bound and strongly validate sync requests; add auth/API abuse controls.
4. Add security headers, `metadataBase`, corrected service-worker routes/cache version, and production PWA upgrade tests.
5. Fix search destinations and dishonest clickable rows; add direct regression tests.
6. Add CI for Prisma validate/generate, typecheck, build, and sequential Playwright against disposable PostgreSQL.
7. Document and rehearse preview promotion, migration, backup/restore, monitoring, health checks, and rollback.
8. Then execute the UI/UX refinement plan in small batches, starting with touch targets, accessibility, Dashboard hierarchy, and project recovery prominence.

## Deployment Decision

- **Local/private use:** GO, with normal backups.
- **Private hosted preview:** NO-GO until sync ownership and registration mode are fixed.
- **Public production:** NO-GO until all P0 and P1 deployment gates are verified in a production-like preview.
